# AGENTS.md

**Field Maps** — https://www.fieldmaps.app · repo `rwolffgang/FieldMaps`

`README.md` is the outward-facing description of the same project (what it is, how to run it). This file is the working document: file map, invariants, calibration, gotchas. Keep the two from drifting — a change that alters how the app is run or deployed belongs in both.

Offline-first PWA that shows the user's live GPS position on a pre-georeferenced airsoft field map. No tile server, no backend — everything is computed client-side from a hardcoded calibration. Every scenario now draws the **custom vector map**, rendered from bundled OpenStreetMap data (`scripts/fetch-osm.mjs` → `packages/core/assets/map_osm.geojson`) in that event's theme: the geometry is projected to canvas pixels once (`packages/core/src/osm-map.ts`) and rasterized into canvas tiles (`packages/field-map/src/basemap-layer.ts`), so panning the map moves finished pixels rather than redrawing vectors. The app ships **no map imagery at all** — the retired photo bases live in `reference/legacy-map-images/`. A photo `base` is still supported (`kind: "image"`, see `packages/core/src/scenario.ts`) but nothing uses it; prefer a theme on the shared base.

**The map is a package, and Field Maps is its first host.** The repository is an npm workspace: `packages/core` (`@fieldmaps/core` — the field's content and everything that needs no UI) and `packages/field-map` (`@fieldmaps/field-map` — the `<field-map>` custom element) are what another app installs to show this map; `src/` is the Field Maps app around it (overview, routing, Impressum, updates, install, dosimeter). The element's contract with any host — properties, `navigateTo*` methods, live markers, `fieldmap-*` events, styling — is written down in `packages/field-map/AGENTS.md`, which ships inside the package for another team's coding agent to read. Change the element's public surface and that file changes with it (`npm test` fails otherwise). The workspace packages export their TypeScript under a `source` condition, which the app's `vite.config.ts` and `tsconfig.json` select, so the app always builds them from source; `npm run build:packages` makes the `dist/` a release ships.

## Stack

Vite + Lit + TypeScript, Leaflet (`L.CRS.Simple`) for rendering, `vite-plugin-pwa` (Workbox) for the offline service worker and the self-update (`src/update.ts`). No other runtime dependencies.

## Commands

- `npm install` — restore dependencies (the delivered folder ships source only).
- `npm run dev` — local dev server.
- `npm run build` — `tsc --noEmit` typecheck, then `vite build` into `dist/`.
- `npm test` — every package's tests (transform, themes and data, marker diff, strings), the guards that `packages/field-map/AGENTS.md` names every public member and that no package imports app code, then the dosimeter model.
- `npm run dev:component` — the `<field-map>` test page (`packages/field-map/test-page/`, port 5180): the element on its own, driven like a host would — scenario and theme pickers, external positions, simulated players, two-tab sync over `BroadcastChannel`, an event log. It imports nothing from `src/`.
- `npm run build:packages` — build `packages/*/dist` (Vite library mode + `.d.ts`); `npm pack --workspaces` then makes the tarballs a release carries.
- `npm run preview` — serve the production build locally.

Deploy: `npm run deploy` (`npm run build` + `wrangler deploy`) to Cloudflare, or `npm run build` and publish `dist/` over HTTPS anywhere (GitHub Pages is fine); install as a PWA on the phone. Geolocation requires a secure context, so it will not work from `file://`.

The Cloudflare Worker is still called `mahlwinkel-map` in `wrangler.jsonc`, and the npm package `airsoft-field-map` — both predate the Field Maps name. Renaming the worker would deploy a _new_ worker and leave the `fieldmaps.app` custom domain attached to the old one, so leave it alone unless you are prepared to move the route by hand. Nothing user-visible carries either name.

**Clients already out there update themselves** — no version to bump, nothing to tell anyone. Deploying is the whole rollout: installed apps find the new build within about five minutes of being on screen, immediately on resume or reconnect, and swap over without a prompt unless a map is open in front of someone. `src/update.ts` has the details; the landing page footer shows the build a phone is actually on (`v0.1.0+1a2b3c4`), which is how you check that a rollout landed. To tell players what a build changed, add an entry at the top of `CHANGES` in `src/whats-new.ts`; they see it once, on the next launch after the update.

## The files a user edits

- `packages/core/src/mahlwinkel/scenarios/*.ts` — **one file per playable scenario.** Each picks a `base` (in practice always the shared OSM vector map plus a theme; a photo `image` with its own control points is still supported but unused), the scenario's PoI labels (`poiNames`), and its play-area boundary polygon (`playArea`, `[lat, lng]` points; everything outside is masked). Optionally also `zones` (marked areas: safe zones, "Zivile Zone", …), `headquarters` (faction HQs drawn with their emblem from `packages/core/assets/logos/`), and `lines` (open frontlines). Copy a file, edit it, register it in that folder's `index.ts`. These are the same files another app's `<field-map>` draws, so a fix here reaches it with the next package release.
- `packages/core/src/mahlwinkel/points-of-interest.ts` — the shared registry of physical PoI **coordinates** (same across all scenarios) plus the default label set. `labelPointsOfInterest` memoises on the `poiNames` object it is handed (a module-level object per scenario, so a stable key); the array it returns is shared and must be treated as read-only.
- `src/config.ts` — orders the scenarios' maps for the overview (`mapsByDate`, `runningMap`). Resolving a scenario's base into a drawable map (`scenarioToMap`, `OSM_BASE`) lives in `packages/core/src/mahlwinkel/index.ts`; the smoothing tunables in `packages/core/src/geo.ts` / `heading.ts`. Prefer editing scenario files over any of these.

## File map

- `packages/core/src/transform.ts` — **the core.** GPS → image pixel via a least-squares _similarity_ fit from the control points. Exposes `solveTransform(points)` returning `{ toPixel, toLatLng, metersToPixels, pixelsToMeters, bearingToScreenDeg, scale, rmsMeters }`. `toLatLng` is the closed-form inverse of `toPixel` — a similarity has no shear, so the 2×2 inverts exactly — and it is what lets a spot the player picked on the map, which exists only as pixels, be navigated to like any other lat/lng.
- `src/config.ts` — the overview's order of the maps (see above).

- `packages/core/src/mahlwinkel/` — the field's content: `scenarios/` (per-scenario labels, play area, zones; `scenarios/index.ts` registers them), `points-of-interest.ts`, and `index.ts` (`OSM_BASE`, `scenarioToMap`, `MAPS`, `getMap`, `getScenario`, `scenarioPoiIds`). Exported as `@fieldmaps/core/mahlwinkel`. A PoI's `kind` (`"turbine"` / `"checkpoint"`, from `WIND_TURBINE_IDS` / `CHECKPOINT_IDS`) is what decides its glyph; the element never looks at ids for that.
- `packages/core/src/scenario.ts`, `poi.ts`, `map-definition.ts` — the data model (`Scenario`, `Zone`, `EventSchedule`, `PointOfInterest`, `MapDefinition`, `comparePointsOfInterest`).
- `packages/core/assets/` — `map_osm.geojson` and `logos/`, served by URL: `fieldMapsAssets()` (`packages/core/vite-plugin.mjs`, imported as `@fieldmaps/core/vite`) serves them from the dev server and writes them into the build at the root, where `<field-map>` looks by default and the precache picks them up.

- `packages/core/src/geo.ts` — `watch(onFix, onError, { smoothing, snapDistanceM })` wraps `watchPosition`, emits a `Fix { lat, lng, accuracy, heading, speed }`, applies light EMA smoothing with a snap-on-teleport (`POSITION_SMOOTHING`, `SNAP_DISTANCE_M`). Also the navigation math: distance, bearing, turn hints.
- `packages/core/src/heading.ts` — compass. `watchHeading(onHeading)`, plus `needsPermission()` / `requestPermission()` for iOS. Circular-mean angle smoothing.
- `packages/field-map/src/field-map.ts` — the `<field-map>` custom element (Lit) wrapping Leaflet, published as `@fieldmaps/field-map`. It resolves its `scenario` property through `@fieldmaps/core/mahlwinkel`, runs the device sensors itself (`sensors.ts`: the GPS watch — started the first time the element is visible with a scenario, never before, then kept for the session — the compass and the iOS "Enable compass" button, the GPS error toast, the screen wake lock), coalesces position and heading into one `applyPosition` per animation frame, and reports to its host through `fieldmap-*` events. Everything around the map that is not the map — the ‹ button, install bar, dosimeter, update banner — is the host's, handed in through the `topStart` / `topEnd` / `topNotice` / `bottomNotice` hooks, which place it inside the element's own rows (the top of the screen is one flex column, `.fm-top`, so nothing restates another row's height). It bakes each scenario's geometry, hands it to the basemap as a `TileScene`, and owns everything that is **not** part of the basemap: the position marker and accuracy circle, the navigation route, the PoI dots and turbine glyphs, the HQ emblems, the zone name labels, the **sticky axis labels** (the squares' column letters and row numbers held against the top and left edges of the screen while the map scrolls under them — at a fixed zoom the whole strip is translated by one style write per frame and only the square running off each end is displaced, `syncGridAxis` / `updateGridAxis` / `placeAxis`; the letters take a row of their own above the PoI select via `--stack-grid-axis`), follow/recenter, and the layer **toggles** (PoI id labels, grid, boundary mask, zones, HQs, own marks — persisted; each shown only when applicable, and grid/mask/zones apply by repainting the basemap rather than adding a layer). The PoI `<select>` option list is wrapped in Lit's `guard()` on the map id: `dragstart` clears `following`, which is `@state`, so without that every drag began by rebuilding ~80 `<option>`s. A `ResizeObserver` re-fits when the container gains size (0×0 cold start). Navigation can be started four ways by the player — and by the host through `navigateToPoi` / `navigateToCoordinates` / `navigateToMarker` — all through `startNavigation`, which records who started it (`source`) and reports every change in `fieldmap-navigation`: the PoI select, the **"Navigate here" button** in a dot's popup, a **double-click on the dot**, or a **long press on any spot that is not a PoI** (`onMapHold`). The last one exists because the numbered PoIs are the buildings the organiser thought to number, while a lot of what a player walks to — a treeline, the corner a squad said it would hold — is not one of them; it asks with the same popup a dot gives, and the picked spot joins the machinery as a PoI under the reserved id `__here__` (`customTarget`) rather than as a second kind of target running beside it, named by its grid square when the grid is on screen to read that against. Three things make the gesture work: `tapHold: true` is set explicitly, because Leaflet only enables its `contextmenu` simulation for a browser it recognises as mobile Safari and an installed PWA's user agent has dropped the "Safari" token — exactly this app's case; Android fires both its own `contextmenu` and Leaflet's, so `onMapHold` ignores a second one at the same place within a second; and the PoI markers answer `contextmenu` themselves, which is what keeps a press that landed on a dot from being read as a press on the ground under it (Leaflet passes a mouse event to the map only when no layer under it listens). Hovering a dot still just labels it — the popup is the version you can act on, so it closes the tooltip while it is open, and its auto-pan padding is measured off the live chrome (`chromeInsets`) rather than restating the CSS row heights. **A PoI is drawn once, and whatever is drawn is the tap target** (`bindPoiInteractions` puts the same label/popup/double-click on all three): a turbine gets its glyph, a road barrier (`kind: "checkpoint"`, today only the Schranke, which only OP Tschernobyl names) gets a boom-gate glyph, a building with a faction emblem on it gets the emblem — the scenarios place several HQs exactly on a numbered building, so `samePlace` pairs them and the dot is left off. Emblems only stand in while the HQ layer is shown, which is why toggling it rebuilds the dots. **A compass reading is not a new position:** `applyPosition` compares the fix against `placedFix` — the one the layers were actually placed for, cleared by `loadMap` because a new calibration puts the same coordinates on a different pixel — and a heading-only update then writes the arrow's rotation and the turn hint and nothing else. Everything it skips is per-event Leaflet work: two vector paths reprojected, the marker repositioned, and a `panTo` that fires `moveend` even for a zero offset and so walks the basemap's whole tile set (measured, while following, at 60 Hz on a desktop: 163 µs and one `moveend` per compass event, against 3.8 µs and none now).
- `packages/field-map/src/markers.ts` (+ the pure `marker-diff.ts`) — **live markers**, the host's `markers` array: other players, objectives. Diffed by id on every set, so a host sending dozens once a second moves markers rather than rebuilding them; their own pane between the PoIs and the player's dot (`own-position`, which nothing covers); the accuracy ring drawn inside the icon and resized per zoom frame, not an `L.Circle` (invariants 7 and 8); stale after `staleAfterMs`; hidden per `layer` from the ⚙ menu. A navigable marker is a navigation target under `__marker__:<id>` and is followed as it moves.
- `packages/field-map/src/types.ts`, `strings.ts` — the public shapes (`MapMarker`, `NavigationState`, `FieldMapEventMap`, …) and the element's German/English texts (moved out of `src/i18n.ts`; a host overrides them through `strings`).
- `packages/field-map/AGENTS.md`, `llms.txt`, `test-page/` — the integration guide another app's agent reads, its index, and the standalone page that exercises every API.
- `src/map-screen.ts` — `<map-screen>`, Field Maps' map screen: `<field-map>` plus this app's chrome, handed to the element through its hooks — the ‹ back to the overview, the dosimeter trefoil and its one-time hint, the "new version" banner `main.ts` drives (`updateBanner`), and the **install bar**. The install bar (first row of the HUD, via `bottomNotice`): event links get passed around directly — `?map=de` in a group chat — so a good share of players land straight on a map and never read the page explaining any of this. The bar holds itself to three rules: it waits for the first GPS fix, so it is asking someone who has just watched the app work rather than someone staring at a blank map; it stays away while a navigation is running, since it would cover the one thing they are walking towards; and dismissing it is remembered. On iOS its button unfolds the gesture in place rather than sending the player back to the overview and costing them the map they are standing on. It hosts the dosimeter dialog too, feeding it from `fieldmap-fix` and `fieldmap-guidance`, and passes `attribution: false` because the overview and the Impressum already credit OpenStreetMap.

- `packages/core/src/marks.ts` — the player's **own marks**, kept per map id in `localStorage` (`<storagePrefix>-marks`, so `field-map-marks` in Field Maps; `markStore(key)`) as lat/lng, never pixels, so a recalibration does not move them; an in-memory copy keeps them for the session when storage is unavailable. `<field-map>` creates them two ways — a **"Mark" button in the long-press popup** (next to "Navigate here") and the **flag button beside recenter**, which drops one at the current fix (shown only once there is an on-field fix) — draws them as markers (`syncMarks`; they change at a tap, so they are layers, not basemap paint), lists them in an optgroup of the PoI select, and navigates to them like a PoI under the reserved id `__mark__:<id>` (`markTargetId`). A mark's popup offers navigate, rename (`window.prompt`) and a two-tap delete; deleting the running target ends the navigation. A new mark opens its popup at once (the default "Markierung N" is the thing they will want to change), and setting one while the marks layer is toggled off turns it back on.
- `src/dosimeter-view.ts` — the `<dosimeter-view>` **prop radiation meter** for the Stalker games, drawn as a battered Soviet ДП-5В and offered from the map's top row (yellow trefoil, left of the gear) on any scenario with `dosimeter: true` — today only OP Tschernobyl. It measures nothing. **Four sources** move the needle, the hottest wins, and a row of green **source lamps** says which one is doing it (ЗОНА · ОБЪЕКТ · ПЕЛЕНГ · СКАН, German/English tape labels), because a needle moving for reasons a player cannot see reads as broken: the `biohazard` zones (the only source that reaches the alarm), radiating objects (every building on the map lifts the needle a little — about 32, lighting ОБЪЕКТ; every faction HQ plus the scenario's `radiatingPois` reach yellow, 45; turbines and the Schranke are not buildings and stay out), direction finding while a navigation runs (objects are ignored meanwhile), and the **СКАН** button — hold it and the counter jumps to yellow within half a second, then builds steadily — alarm at ~4 s, full red at ~9 s; let go and it falls back over 2 s, for roleplay ("scanning an artifact"; pointer capture, keyboard Space/Enter, no iOS long-press callout). Without a fix the field reads background, the panel says НЕТ GPS, and СКАН still works. Analog dial 0–5 times a range the device always steps by itself (АВТО; 0.05–500 мР/ч full scale, up above 92 % of full scale, down below 60 % of the next one down, one step per 120 ms tick) so the needle stays on the scale; there is deliberately no range switch or overload lamp — they confused players. ТРЕВОГА blinks from level 60 (1 мР/ч). Geiger clicks are synthesised with Web Audio (shaped noise at Poisson intervals whose rate follows the reading), on by default (the trefoil button unlocks audio inside its tap via `primeDosimeterAudio`; one shared AudioContext, suspended while the device is closed and woken again — on return to the foreground and on any tap while it is open — after iOS interrupts it on screen lock; it plays through the iOS silent switch by taking the media/"playback" audio category — `navigator.audioSession` on iOS 17+, a looping silent in-memory WAV `<audio>` on older iOS — which also pauses the player's own music while the device is open), toggled by the ЗВУК switch. The first opening shows an in-world **instruction slip** (ИНСТРУКЦИЯ, text in `i18n.ts`, remembered in `field-map-dosimeter-manual-seen`); the "?" on the case brings it back. Labels are Russian on purpose; the tape strips carry the player's words. Shadow DOM, system fonts only (offline). `map-screen` hosts it in a native `<dialog>` driven by `dosimeterOpen` (closed on every `loadMap`), mounts it only while open (which starts and stops its clock and audio), hands it the zones and radiating objects (`dosimeterSources`), writes each moved fix straight onto its `position` from `fieldmap-fix`, and passes on the navigation guidance from `fieldmap-guidance` (below). The first navigation started on a dosimeter map shows a one-time callout under the trefoil ("Navigiere mit dem Geigerzähler"; tap opens the device, × dismisses, gone by itself after 10 s since it can cover the iOS compass prompt; remembered in `field-map-dosimeter-hint-seen`).
- `src/radiation.ts` — the dosimeter's GPS model, pure and tested (`src/radiation.test.ts`, part of `npm test`), on the dosimeter's 0–100 scale (one decade of dose per 20): the signed distance to each `biohazard` zone (background 10 far off, 50 on the edge, toward 90 deep inside), the distance to each radiating object (its own peak on it — `BUILDING_LEVEL` 32 for an ordinary building, `POI_LEVEL` 45, yellow, for a hot one, both deliberately below the alarm — gone within ~50 m), and the **direction finder** (`levelForBearing`): a narrow lobe around the target's bearing relative to the compass heading, peaking at 50 (~0.3 мР/ч) whatever the distance — direction only, a game tool rather than physics. `<field-map>` reports `{ relativeDeg, distanceM }` in `fieldmap-guidance` on every compass or position update during a navigation, and `map-screen` puts it on the device, null without a compass, on arrival, or when the navigation ends, and the panel then reads ПЕЛЕНГ with the distance.
- `src/install.ts` — **how the app gets onto a home screen**, and the only file that sniffs the user agent. Test users did not work out that Field Maps installs, and the old card is why: it printed the iPhone gesture and the Android gesture side by side, so every reader first had to work out which half was theirs, and Android readers were sent into a browser menu while Chromium had been offering a one-tap install the whole time. `installMethod()` collapses that into one answer per device — `prompt` (Chromium handed us a `beforeinstallprompt`, which we hold and fire behind our own button), `ios` (no API exists, so the gesture is described), `in-app-browser` (a webview, where nothing can be installed and the Share menu has no "Add to Home Screen" to point at — this is how players arriving from the organiser's Instagram posts get there), `manual`, `installed`. The three sniffed cases have no feature test; the good one does, and `beforeinstallprompt` is `preventDefault`ed so Chrome's own mini-infobar does not make the same offer twice in a second visual language. Also owns the map screen's "not now", which is remembered for a fortnight — long enough to cover a whole event weekend.
- `src/landing-view.ts` — the `<landing-view>` overview at `/`: intro, the site chip and the note under the events heading (the app covers **one** field, the Mahlwinkel airfield — say so before someone installs it expecting their own event; the "Field Maps" name is deliberately site-neutral, the coverage is not), the install card and the share button (both below), event cards ordered by date, and the footer links (donations, `robert@wolffgang.de`, GitHub, Impressum). The **install card** renders whichever branch `src/install.ts` picked: a button on Chromium, two numbered steps on iOS with the Share glyph drawn inline (that control carries a symbol and no word on iOS, so naming it in text is asking someone to find something they cannot see), and a neutral "open this in Safari first" card inside a webview. It leads with the reason rather than the gesture — barely any signal on the field — because a test user can follow "add to home screen" perfectly and still not see why they would. The **share sheet** is a native `<dialog>`, so the backdrop, focus trap and Escape come from the browser; it holds the QR code, the URL, a copy button, and `navigator.share` where it exists. `SITE_URL` is written out rather than read from `location`, because the page may well be on a tunnel URL or a bare LAN address and the link handed to someone else has to be the real one.
- `packages/core/src/brand.ts` — the two colours off the app icon (`BRAND_BLUE`, `BRAND_BLUE_DEEP`, `BRAND_ORANGE`). Leaflet needs colours as JS strings, the chrome takes them from CSS, so `styles.css` mirrors them as `--brand-*` / `--accent` / `--accent-warm` at the top of `:root`, and `field-map.css` uses them as the defaults of `--field-map-accent` / `--field-map-accent-warm` (which `refreshStyle()` reads back for the accuracy circle and the route). Change one, change the others. Blue means "you and the app" (position dot, accuracy circle, active controls), orange means "a place on the ground" (PoIs, navigation, the install prompt); everything else stays neutral so those two keep their weight. Per-event map palettes (`accent`, the `osm-map` themes) are separate and stay per-event.
- `src/legal-view.ts` — the `<legal-view>` legal page at `/?page=impressum`: Impressum (§ 5 DDG) and privacy notice, both languages, text in `i18n.ts`. **`OPERATOR` at the top of the file is the one thing that has to be right** — name, summonable postal address, contact email. Missing address lines render as loud orange placeholders rather than disappearing, because an Impressum with no address is the failure worth shouting about. Reachable offline like every other screen, which is why it is a route and not an external page.
- `src/router.ts` — the whole "router": read/write the `?map=` and `?page=` parameters, notify on change and on Back.
- `src/event-schedule.ts` — recurring month/day schedules, German date formatting, and the soonest-first comparator.
- `src/main.ts` — wires the three screens together on route changes (`map-screen` gets the routed scenario, and preloads the last one behind the overview), the update policy (holds a reload while `map-screen.navigating`), and opening a running event. **The position watch is no longer here:** `<field-map>` starts it the first time it is on screen with a scenario (`startSensorsIfShown`), which is still never on the overview — the overview draws no dot and does nothing with a fix, so asking there is a permission dialog over a page that gave no reason for one, and a "no" collected there is only undone in the site settings. Once started it stays on for the session. Position and heading reach the map once per animation frame (`schedulePush` in the element): GPS arrives about once a second but `deviceorientation` fires at the sensor's rate, and nothing the view draws can appear more often than the display refreshes.

- `packages/core/src/transform.test.ts`, `core.test.ts`; `packages/field-map/src/*.test.ts`, `scripts/check-docs.ts`, `scripts/check-boundaries.ts` — `npm test`. Not part of the build (`tsconfig` excludes `*.test.ts`).

- `src/update.ts` — **how a redeploy reaches a phone that never reloads.** Registers the service worker in `prompt` mode and then goes looking for new builds itself: on a five-minute timer while the app is on screen, whenever it returns from the background, and whenever the device reconnects. A browser would otherwise check only on a real navigation, which an installed PWA resumed from the app switcher may not do for weeks. `prompt` is what makes applying the update a decision rather than an ambush: the new build installs and waits, so the running page keeps the assets it started with instead of a fresh precache appearing under executing code. `main.ts` supplies the policy — reload silently off the map or while backgrounded, put a banner up over a live map, and hold off entirely while a navigation is running, since the destination is the one thing a reload would make the player re-enter. The reload itself is ours (`onNeedReload` is handed a no-op): vite-plugin-pwa only reloads when the page was already controlled at registration time, which is false for the very session that installed the app.
- `src/whats-new.ts` — the `<whats-new-view>` **"What's new" dialog**: a native `<dialog>` listing the entries in `CHANGES` (newest first, German/English inline, optional SVG glyph) that this player has not dismissed, shown once at launch over whatever screen the route opened. Dismissal stores the newest id in `field-map-whats-new-seen`. A first-time visitor is never shown it — with no record and no other `field-map-*` key in storage, the newest id is marked seen instead — while a player from before the dialog existed has such keys and gets the newest entry. That decision is made **when the module loads**, before routing opens a map and writes the remembered map id, which would otherwise make every first visit look like a returning one; `main.ts` imports it first for that reason.
- `packages/core/src/glyphs.ts` — pictograms used in more than one place, as SVG markup strings (the map passes them to Leaflet as divIcon HTML, the chrome renders them through Lit). Today the checkpoint boom gate, drawn on the map and in the "What's new" entry about it.
- `src/analytics.ts` — **the visitor count**, and the only thing this app sends anywhere. Loads Cloudflare's cookie-less beacon on start-up, gated on `BEACON_TOKEN` (empty = off, which is how it ships) and on a production build, so `npm run dev` never reaches the numbers — use `npm run preview` to see it fire. It is a beacon rather than a read of the server logs because every screen is precached: an installed app answers its own navigations from the service worker, so the origin sees first visits and update checks, not use. **Nothing may ever be stored on the device here.** No cookie and no visitor id is exactly what keeps this out of § 25 TDDDG consent territory and lets it run on legitimate interest without a banner; adding one would make the privacy notice in `i18n.ts` false and require a consent dialog. Turning this on or off means editing the `Reichweitenmessung` / `Visitor counting` sections in `i18n.ts` to match.
- `packages/core/src/osm-map.ts` — the map's **look**, and the two functions that draw it. `bakeOsm` projects the OpenStreetMap-derived GeoJSON (`packages/core/assets/map_osm.geojson`, 379 features / ~9k vertices) into canvas pixels **once per map load**, into flat `Float32Array` rings with a bounding box each — a vertex buffer, in the game-engine sense. `paintTile` then paints one tile of the map from that: surround, ground, features in `DRAW_ORDER`, tone wash, grid, out-of-bounds mask, zones, frontlines, edge. `bakeShape` does the same for a play area, a zone or a frontline. Ships six **themes**, one per event's printed tactical map: `opt` (warm sepia), `m24` (cold dark satellite), `de` (near-black), `asd` (green surround), `lso` (cool blue-grey), `laf` (grey-green). A scenario's OSM base picks one; a host can override it with `theme` — a name, or an object made with `extendTheme` (a theme is plain data: `THEMES`, `OsmTheme`, and an optional `outOfBounds` whose defaults are the colours `paintTile` used to hardcode). `TileScene.theme` is the resolved object. The hatches (out-of-bounds, safe zones) are canvas patterns built from a small pre-rotated stripe tile and filled in **device space**, so the stripes keep their size on screen and line up across tile seams — that is what the injected SVG `<pattern>`s used to do. A `biohazard` zone (the printed maps' "Verstrahlt" areas) uses the same device-space fill with a tile of biohazard symbols, drawn from the symbol's geometric construction in `drawBiohazard` rather than shipped as an image. Fully offline: the data is bundled and precached.
- `packages/field-map/src/basemap-layer.ts` — `BasemapLayer`, an `L.GridLayer` whose tiles are `<canvas>` elements painted by `paintTile`. **This is why dragging is cheap.** Everything static used to be Leaflet vector layers, which Leaflet re-clips and re-rasterizes on every `moveend` — reallocating each renderer's canvas as it goes — so keeping the map painted through a drag meant firing `moveend` several times per gesture and paying that price each time (measured: 21 full canvas redraws and ~26 ms of main-thread work for one drag across the field, against ~1.5 ms now). A tile is rasterized once, in about a quarter of a millisecond, and afterwards only translated. Tiles exist **only over the canvas rectangle** (`bounds`), so past the edge of the field there is nothing to draw and the container's background — set to the theme's surround — is the border. Three settings are load-bearing: `updateWhenIdle: false` (Leaflet defaults it to `true` on mobile, which would load tiles only after the pan stops), the GridLayer `minZoom`/`maxZoom` opened out (its default floor of 0 rejects every tile on a map whose zooms are negative), and the one-tile pad in `_getTiledPixelBounds` (`keepBuffer` only decides what is _kept_, not what is built ahead). `MAX_PIXEL_RATIO` caps a tile's backing store at 3 device pixels per CSS pixel: `MAX_OVERSAMPLE` bounds the oversample _factor_, not the result, so on a 3× phone it alone asked for 4.5 — a 1152² canvas per 256 px tile, forty-odd of them live, a couple of hundred megabytes on the device least able to spare it. A 2× phone lands on 3 either way, so the cap only ever trims the extreme.
- `reference/tactical-maps/` — the organiser's printed Taktikkarten, one per event, downloaded from `airsofthelden-events.com/<event>/taktikkarte`. **Source material, not app assets** — they live outside `public/` so they are not bundled or precached. Every PoI coordinate, play area, zone and HQ position in `src/` was read off these; keep them so the numbers can be re-derived or checked.
- `packages/core/assets/logos/` — faction emblems (GOF, KGG, Miliz, Task Force, Kartell, Rebellen, TERRA, UCRF, the TNO factions, Delta, Ghost), pulled from the organiser's site and normalised to 256×256 PNG — except `tno-baltische-brigade.png` and `tno-sekte.png`, which were redrawn from the 2026 OP Tschernobyl map because the site does not carry it. Referenced by `Headquarters.logo` (resolved against the element's `assetBase`), so these **are** bundled — and shipped in the package, though not under its MIT licence (see `LICENSE`).
- `scripts/make-qr.mjs` → `public/qr-fieldmaps.svg` — the share sheet's QR code, baked once. It encodes the site root and nothing else, so it is the same square forever and generating it per open would be work repeated for a constant. The encoder is in the script (byte mode, error correction M, versions 1–6; the URL is 25 bytes, so version 2) rather than a dependency — the app ships Leaflet and Lit and nothing else. The SVG carries its own white ground, because a code needs dark modules on a light field with a light quiet zone and every surface on that page is near-black. The committed file was checked against an independent encoder module-for-module, then rasterised and read back with a real decoder.
- `scripts/make-screenshots.mjs` → `public/screenshots/` — the manifest's screenshots, which are what decide **which install dialog Chrome shows**: without them a thin bar naming the site, with them a card showing the app. Needs the dev server up and fetches Puppeteer on demand (not a dependency, and it drives the Chrome already on the machine). It grants geolocation and puts the fix in the middle of the field, so the dot is in frame — a screenshot of the app not knowing where you are would advertise the one thing it is for as broken. Re-run when the map's look changes, and keep the `sizes` in `vite.config.ts` matching the files. They are `globIgnores`d out of the precache: the install dialog is by definition shown _before_ there is a service worker, so precaching them would put a megabyte on every phone for a picture none of them will request.
- `scripts/fetch-osm.mjs` — one-off, reproducible download of OSM data from the Overpass API into `packages/core/assets/map_osm.geojson` (kept compact: `.prettierignore` skips `*.geojson`, which Prettier would otherwise pretty-print to half again its size on every phone). The only step that reaches the network **for app data**; run `node scripts/fetch-osm.mjs` to refresh the data. It also prints the control points + canvas dimensions to paste into `OSM_BASE` in `packages/core/src/mahlwinkel/index.ts`.

## Screens and URLs

Three screens, two query parameters (`src/router.ts`):

- `/` — the overview (`src/landing-view.ts`): what the app is, then one card per event.
- `/?map=<id>` — that event's map, opened directly.
- `/?page=impressum` — Impressum and privacy notice (`src/legal-view.ts`), linked from the overview's footer.

A **query parameter**, not a path or a hash, so a bookmarked map resolves on any static host without rewrite rules — which matters because this ships as an offline PWA and a saved link has to open from the service worker cache with no server in reach. Room to extend later (`&poi=630`).

All three views stay in the DOM and `main.ts` toggles `hidden`, rather than tearing the map down: `<field-map>` already re-fits when its container gains size (it has to, for the 0×0 cold start), so returning to a map is instant. The map-only chrome (status toast, compass prompt, update banner) lives inside the element or its hooks, so it is hidden with the screen.

Event cards are real `<a href="?map=…">` elements with the click intercepted — long-press-to-copy, open-in-new-tab and bookmarking all keep working. That is the point of the screen.

## Event ordering

`src/event-schedule.ts` stores each event as month/day only (no year), because they recur annually — that keeps the scenario files from going stale every January. `mapsByDate()` sorts the overview soonest-first, counting a running event as zero days away, so the map you need is at the top on the day you need it. Style variants (no `schedule`) sort last. It is a function, not a constant, because the answer depends on today's date and people leave this open for a whole weekend.

While an event is running, a bare launch (`/`, no `?map=` or `?page=`) **opens that event's map directly** (`runningMap()` in `config.ts`, `openRunningEvent` in `main.ts`). It pushes the map on top of the overview, so Back and the ‹ button still reach the list; it happens once per tab (`field-map-auto-opened` in `sessionStorage`), so going back to the overview sticks, even through the silent update reload; and it only fires when exactly one event is running, since two overlapping ones would make it a guess.

## Invariants — do not break these

1. **Pixel convention.** Everywhere except the Leaflet boundary, a pixel is an _image_ pixel: origin top-left, x right, y **down**. `toPixel` returns image pixels. Keep it that way; it's the debuggable convention.

2. **There are two separate y-flips. Keep them separate.**
   - Inside `transform.ts`, the forward model uses the _reflection_ form `px = a·E + b·N + c`, `py = b·E − a·N + d`. The minus sign is what maps north-up ground coordinates to image-y-down. A no-rotation map solves to `b = 0`.
   - At the Leaflet boundary, `field-map.ts::px2ll(px, py)` does `[MAP_HEIGHT - py, px]` to convert image-y-down into CRS.Simple's y-up. `BasemapLayer.createTile` inverts exactly that to get from a tile coordinate back to canvas pixels, and it is the only place that does.
     Do **not** try to collapse these into one step; they live in different layers for a reason, and merging them is the classic way to get an upside-down or mirrored map.

3. **Similarity, not affine.** The fit is translation + rotation + uniform scale (4 unknowns), solved via normal equations. Do not "upgrade" it to a full 6-parameter affine — affine allows shear and per-axis scaling, which lets noisy GPS distort the map.

4. **Bearing → screen rotation goes through `bearingToScreenDeg`.** It accounts for the map's own rotation relative to north, so the heading triangle points true even when the printed map isn't north-aligned. Don't compute triangle rotation any other way.

5. **The heading triangle rotates an _inner_ element.** Leaflet owns the marker's outer `transform` (positioning translate). Rotation is applied to `.pm-arrow` inside the divIcon. Rotating the outer element will fight Leaflet.

6. **`<field-map>` renders in light DOM** (`createRenderRoot() { return this; }`) so Leaflet's global CSS applies. Both stylesheets (Leaflet's and `field-map.css`, imported `?inline`) are injected once, at the **start** of `<head>` (`injectStyles`), so a host's own stylesheet comes later and wins a tie; every rule is scoped `field-map …` for the same reason, and the `--field-map-*` defaults are declared on `:where(field-map)` so any host rule replaces them. Don't move it into shadow DOM without also injecting Leaflet's stylesheet there — and note that host overrides would then stop working.

7. **Anything that does not move belongs in `paintTile`; only things that follow the user may be Leaflet layers.** Terrain, grid, mask, zones, frontlines and border are painted into the basemap's tiles and cost nothing to drag. A Leaflet vector layer is re-clipped and re-rasterized every time the view settles, and a full-viewport one several times per gesture — which is the exact cost this design exists to avoid. Adding a static shape as an `L.polygon` will not look wrong; it will just quietly make dragging heavy again. Text is the standing exception: labels have to stay upright and screen-sized, so zone names, PoI dots and HQ emblems are markers.

8. **Never move a vector path while the zoom is changing.** Leaflet does not redraw the accuracy circle or the route line through a zoom: it leaves their geometry in the coordinate space of the zoom the renderer last settled at and CSS-scales the renderer's container to cover the difference. A path reprojected mid-gesture is written in the live zoom's coordinates and then scaled a second time on top — it grows at the square of the pinch and slides off the dot. `field-map.ts::deferPathsWhileZooming` holds those two writes between `zoomstart` and `zoomend` and replays the fix that arrived meanwhile; anything new that follows the user through a `L.Path` has to go through the same gate. Markers are exempt: their pane is not transformed, so Leaflet repositions them per frame.

9. **`<field-map>` never imports from `src/`, and never touches the network** beyond fetching its own two assets. Another app installs only the packages; anything they reach in the app would not be there, and the element must stay something a host can ship without a privacy notice of its own (`scripts/check-boundaries.ts` enforces the first half). Field Maps-only behaviour (dosimeter, install bar, routing) goes into `src/map-screen.ts` through the element's hooks and events, never into the element. Its `localStorage` keys keep their `field-map-*` names under the default `storagePrefix`: renaming one loses every player's marks or layer switches, and `whats-new.ts` reads the prefix to tell a returning player from a new one.

10. **The service worker never activates on its own.** `registerType: "prompt"` and `workbox.skipWaiting: false` in `vite.config.ts` are a pair, and `src/update.ts` is the only thing that releases a waiting build. Switching either back to the eager form (`autoUpdate`, `skipWaiting: true`) hands a running page a precache it was not built against — the new worker starts answering the old app's requests, and the player finds out when something they tap fetches an asset that no longer exists. The update still has to be _found_ eagerly; that is the timer's job, not the worker's.

## Where the coordinates come from

Every number in `points-of-interest.ts` and the scenario files was derived from the maps in `reference/tactical-maps/`, by fitting the same similarity transform the app uses (image pixels ↔ GPS) and inverting it. Accuracy differs by source, so treat them differently:

- **LIGHT-SIM** is the anchor. Its map carries a real UTM zone 32N grid at 100 m spacing (192.7 px per 100 m, detected from the image). Projecting the shared PoIs onto it lands them squarely on their buildings — that is the cross-check that validates the whole registry.
- **Dark Emergency 2026** fitted to **3.0 m RMS** from the five named wind turbines. Its extra buildings (423, 500, 505, 508, 808, 824, Tango) are that good.
- **Lost Airfield** fitted to **9.8 m RMS** from 28 buildings shared with the other maps. Its 31 exclusive buildings are good to ~10 m.
- **Play areas, zones and frontlines were traced by hand** off the printed maps and are only good to a few tens of metres. LIGHT-SIM's own map says as much: "Tatsächliche Spielfeldgrenzen werden durch Flatterband markiert." Refine them from a walked GPS track when you can.

Beware that the events renumber things: Dark Emergency 2026's "612 Fahrzeughalle" is the building every other legend calls 613, and the same id can carry a different name per event (610 is Esco Bar, Laborkomplex or Stalker Bar depending on the game). Ids are physical; names are per scenario.

## Calibration & correctness

- `solveTransform` logs `rmsMeters` on startup (`[calibration] RMS error: … m`). A mistyped control point shows up as a large residual — treat that as the first-line check after any calibration change.
- Reference origin is the first control point; the equirectangular ENU projection is accurate to sub-meter over a few hundred meters, which is the whole point of keeping the field small.
- After editing the transform math, run `npm test`. Epsilons there are set to realistic floating-point tolerances (~1e-3), not zero — the tiny residual is projection curvature, not a bug.

## Platform gotchas

- **HTTPS required** for geolocation; must be installed/served over TLS before offline use works.
- **The GPS prompt is map-gated.** `<field-map>` calls `watchPosition` only once it is visible with a scenario (a tapped event or a deep-linked `?map=`; `map-screen` is `hidden` on the overview, so the element is 0×0 there), so anything that wants a fix — or a test that looks for one — has to be on a map route first.
- **The compass prompt is decided by what the sensor does, not by the API.** `DeviceOrientationEvent.requestPermission()` used to mean iOS; Chromium has it now too, laptops included, and answers a tap with `"prompt"` when there is nothing to grant. So `<field-map>` starts listening at once and decides from the first second (`packages/field-map/src/compass-decision.ts`): a real heading → on; an empty reading (Chromium without a sensor) → no compass, unless the device is touch-first with the API (a phone whose sensor is gated) → the "Enable compass" button; silence (iOS before permission) → the button if the API exists. After a granted tap, an empty reading or silence means no compass rather than asking again. Only an explicit `"denied"` puts up "Compass permission denied". Whether real Android Chrome gates its compass was not checked on a device when this was written.
- **Heading source:** `<field-map>` (`push`) prefers GPS course when moving faster than `GPS_HEADING_SPEED`, falling back to the magnetometer when stationary, because metal replicas and batteries deflect the compass.
- **Tree cover** degrades GPS to 5–15 m; the accuracy circle is drawn deliberately so the user sees this. Don't over-smooth position (`POSITION_SMOOTHING`) to hide it — that just makes the dot lag reality.
- **`sw.js` must never be cached.** `public/_headers` serves it `no-cache`, and that one line is the whole update path: a client asks for a new build by re-fetching that file, so an edge or browser copy of yesterday's `sw.js` is an app that can no longer update. Any host this ships to has to honour it (Cloudflare Workers assets does; so does GitHub Pages, which sets short-lived caching on HTML and JS anyway). Everything under `/assets` is content-hashed and cached forever, which is the other half of the same arrangement.
- **Precache size:** the map image is precached for offline use. If a large map exceeds the Workbox limit, raise `maximumFileSizeToCacheInBytes` in `vite.config.ts`. More important than the limit is the total: `globPatterns` sweeps up **every** image in the build — `public/` and the package assets `fieldMapsAssets()` emits — referenced or not, and a player installs the app on mobile data. Anything no scenario loads belongs in `reference/` (see `reference/legacy-map-images/`), and photo bases ship as WebP — `map_m24` alone was 2.2 MB as a PNG against 215 KB re-encoded.

## Conventions

- TypeScript strict mode; keep heavy logic in the framework-agnostic modules of `@fieldmaps/core` (`transform`, `geo`, `heading`, `osm-map`) and orchestration in the element / `main.ts`.
- Field Maps-only features go in `src/`, through `<field-map>`'s hooks and events — never into the packages (invariant 9). A new public member of the element goes into `packages/field-map/AGENTS.md` in the same change.
- No new runtime dependencies without a clear reason — self-containment is a feature here.
- Prefer editing `config.ts` over hardcoding values in modules.
